סודות (secrets)

סיסמאות ומפתחות לא נמצאים בגיט אף פעם. בריפו של השרת יש קובץ .env.example עם רשימת כל המשתנים בלי הערכים הרגישים. את הערכים האמיתיים מקבלים מליד בהודעה פרטית, ושמים בקובץ .env אצלכם (הוא כבר ב־.gitignore). ב־Preview ובפרודקשן אותם משתנים מוגדרים כ־Environment Variables בפרויקט ה־API ב־Vercel, ורק הלידים מנהלים אותם.

משתנה למה הוא משמש מאיפה מקבלים
NODE_ENV, PORT מצב הריצה והפורט (ברירת מחדל 3000) כבר ב־.env.example
APP_ORIGIN הכתובת שהדפדפן פותח (HTTPS). השרת מפנה אליה כל בקשת HTTP ובודק מולה את ה־Origin בבקשות שמשנות נתונים כבר ב־.env.example (לא רגיש)
MONGODB_URI כתובת החיבור למסד הנתונים ליד (רגיש)
CLOUDINARY_CLOUD_NAME, CLOUDINARY_API_KEY, CLOUDINARY_API_SECRET העלאה והורדה של קבצים שם הענן כבר בקובץ; המפתח והסוד מליד (הסוד רגיש)
GMAIL_USER, GMAIL_APP_PASSWORD שליחת מיילים מחשבון המועדון המשתמש כבר בקובץ; סיסמת האפליקציה מליד (רגיש)
שימו לב: מסד נתונים משותף כרגע סביבת הפיתוח המקומית והפרודקשן משתמשות באותו מסד נתונים. לא מריצים סקריפטים שמוחקים או משנים נתונים בכמויות, ונתוני בדיקה מסמנים במיילים שנגמרים ב־@test.local. אם משהו נראה לא בטוח, שואלים ליד לפני.
לעולם לא: לא מעלים .env לגיט, לא מדביקים סודות בצ׳אט קבוצתי או ב־PR, ולא שמים סוד במשתנה שמתחיל ב־VITE_ (כל מה שמתחיל ב־VITE_ נכנס לקוד שהדפדפן מוריד, וכל אחד יכול לראות אותו).

4הרצה מקומית של שני הריפוזיטוריז

שלב 1: clone לשניהם, אחד ליד השני

mkdir ColmanDevClub && cd ColmanDevClub
git clone https://github.com/colmandevclub/ColmanDevClub-Server.git
git clone https://github.com/colmandevclub/ColmanDevClub-New-Website.git

שלב 2: השרת (API)

cd ColmanDevClub-Server
nvm install 22 && nvm use 22
pnpm install
cp .env.example .env      # Windows: copy .env.example .env
# fill in the secret values you got from a lead
pnpm dev                  # http://localhost:3000

pnpm dev מריץ את השרת עם tsx watch, כלומר כל שמירה של קובץ מפעילה אותו מחדש. בהפעלה, הקובץ src/config/env.ts בודק עם zod שכל משתני הסביבה תקינים. אם משהו חסר או שגוי, השרת לא יעלה ויכתוב בדיוק מה הבעיה.

תקלה ידועה ב־main: pnpm dev נופל עם ReferenceError: require is not defined, בגלל השורה import helmet = require('helmet') ב־src/app.ts (tsx לא תומך בה). עד התיקון ב־KAN-113, מריצים גרסה בנויה (בלי watch): 
pnpm build && node --env-file=.env dist/server.js

בדיקה בטרמינל אחר. השרת מחייב HTTPS בכל סביבה, אז בקשת HTTP ישירה מקבלת הפניה (308) ל־APP_ORIGIN. זה סימן שהשרת עלה: 

curl -i http://localhost:3000/api/v1/health
# HTTP/1.1 308 Permanent Redirect
# Location: https://localhost:.../api/v1/health

# the same request as if it came through an HTTPS proxy:
curl -H "X-Forwarded-Proto: https" http://localhost:3000/api/v1/health
# {"status":"ok","message":"ColmanDevClub API is healthy"}

שלב 3: האתר (Web), בטרמינל נפרד

cd ColmanDevClub-New-Website
nvm use                   # reads .nvmrc → Node 22
pnpm install
pnpm dev                  # http://localhost:5173

בצד הלקוח אין כרגע משתני סביבה, אז אין צורך ב־.env. פתחו את http://localhost:5173.

שלב 4: לוודא ששניהם מדברים

שרת הפיתוח של Vite מעביר (proxy) כל בקשה ל־/api אל http://localhost:3000. כלומר הקוד בדפדפן תמיד קורא ל־/api/v1/..., בדיוק כמו בפרודקשן: 

curl http://localhost:5173/api/v1/health

אם קיבלתם את אותה תשובה, הכול עובד. אם השרת רץ על פורט אחר, עדכנו את DEVELOPMENT.API_TARGET בקובץ src/constants/development.ts.

זרימת HTTPS מקומית

הקוקיז של ההתחברות הם Secure, והשרת בודק Origin ו־X-CDC-Request: 1 בכל בקשה שמשנה נתונים, אז גם מקומית הדפדפן צריך לעבוד מול מקור HTTPS אחד:

  1. הדפדפן פותח את Vite ב־https://localhost:5173 (תעודה מקומית).
  2. Vite מעביר את /api לשרת ב־http://localhost:3000 ומוסיף X-Forwarded-Proto: https.
  3. ב־.env של השרת: APP_ORIGIN=https://localhost:5173, כלומר הכתובת שהדפדפן פותח ולא הפורט של השרת.
עדיין לא עובד ב־main: כרגע Vite רץ על HTTP בלי X-Forwarded-Proto, ולכן curl http://localhost:5173/api/v1/health מקבל 308 במקום תשובה. התיקון, כולל פקודת בדיקה קבועה, נמצא ב־KAN-113 (S-0.21). עד שהוא ממוזג, עבדו מול השרת ישירות עם ה־curl משלב 2.
מה קורה ב־pnpm install? חוץ מהתקנת החבילות, הוא מפעיל את Husky, שמתקין git hook: לפני כל commit רץ lint-staged, שמפרמט ובודק רק את הקבצים ששיניתם. אם ה־commit נכשל, תקנו את מה שהוא כותב ונסו שוב.

6כללי כתיבת קוד

מקור האמת לממשק: Claude Designאיך כל מסך נראה (פריסה, צבעים, טיפוגרפיה, ריווחים, מצבי טעינה וריק) נקבע ב־קובץ העיצוב ב־Claude Design שמשותף עם הצוות. לפני שבונים מסך פותחים אותו שם ובונים לפיו. אם משהו חסר או לא ברור בעיצוב, לא ממציאים: שואלים ליד, והעיצוב מתעדכן קודם ורק אז הקוד.

1. RTL: רק מחלקות לוגיות

האתר כולו בעברית, <html lang="he" dir="rtl">. ב־Tailwind לא כותבים "שמאל" ו"ימין" אלא "התחלה" ו"סוף", כך שהעיצוב מתהפך נכון לבד.

❌ אסור ✅ במקום משמעות
ml-4 / mr-4 ms-4 / me-4 margin בהתחלה / בסוף
pl-4 / pr-4 ps-4 / pe-4 padding בהתחלה / בסוף
left-0 / right-0 start-0 / end-0 מיקום
text-left / text-right text-start / text-end יישור טקסט
rounded-l, border-r rounded-s, border-e פינות וגבולות

יש כלל ESLint משלנו (tools/eslint/no-physical-direction.js) שחוסם את המחלקות האסורות, וה־CI ייכשל אם הן מופיעות. כותבים שמות מחלקות מלאים בקוד ולא מרכיבים אותם מחלקים ('m' + side), כי אז הכלל לא יכול לבדוק אותם.

טקסט מעורב עברית־אנגלית: מונח באנגלית בתוך משפט עברי עוטפים ב־<bdi>. מיילים, כתובות, טלפונים וקוד מקבלים dir="ltr". 

<p>השיעור הבא: <bdi>React Hooks</bdi></p>
<a href="mailto:colmandevclub@gmail.com" dir="ltr">colmandevclub@gmail.com</a>
<div className="ms-4 ps-2 text-start">...</div>

2. zod: כל קלט עובר סכמה

כל body, query ו־params שמגיע לשרת נבדק מול סכמת zod דרך ה־middleware validate(schema), לפני שהוא מגיע ל־controller. הסכמה בשרת היא מקור האמת. באתר יש עותק שלה, שמשמש לבדיקת טפסים עם react-hook-form. 

// server: src/schemas/application.schema.ts
export const createApplicationSchema = z.object({
  fullName: z.string().min(2),
  email: z.email(),
  phone: z.string().regex(/^05\d{8}$/),
})
export type CreateApplicationInput = z.infer<typeof createApplicationSchema>

// route
router.post('/', validate(createApplicationSchema), controller.create)

3. Policies: כל נתיב מצהיר מי מורשה

הרשאות נכתבות כפונקציות פשוטות ב־src/policies/, ומחוברות לנתיב עם authorize(policy). לא כותבים if (user.role === 'admin') בתוך controller או service. כל policy נבדקת בטסט מול טבלת ההרשאות ב־REQUIREMENTS §3. 

// src/policies/materials.policy.ts
export const canManageMaterials = (u: User, yearId: string) =>
  isAdmin(u) || isMentorOfYear(u, yearId)

// route
router.post('/weeks/:id/materials', authenticate, authorize(canManageMaterials), validate(schema), controller.create)

4. פורמט שגיאות אחיד

כל שגיאה מהשרת חוזרת באותו מבנה, כך שהאתר יודע להציג אותה בלי לנחש: 

{ "error": { "code": "VALIDATION_ERROR", "message": "...", "fields": { "phone": "..." } } }
code HTTP מתי
VALIDATION_ERROR 400 הקלט לא עבר את סכמת ה־zod (הפירוט ב־fields)
UNAUTHENTICATED 401 לא מחוברים, או שהטוקן פג
FORBIDDEN 403 מחוברים, אבל אין הרשאה
NOT_FOUND 404 לא קיים (או קיים ושייך למישהו אחר: לא מגלים את זה)
CONFLICT 409 כפילות, למשל מייל שכבר רשום
RATE_LIMITED 429 יותר מדי ניסיונות

בקוד זורקים שגיאה, וה־errorHandler המרכזי הופך אותה לתשובה במבנה הזה. לא שולחים res.status(500).send('oops') ידנית.

5. עוד כמה כללים

  • קריאות לשרת רק דרך api מ־@/lib/api: הוא כבר מוגדר עם /api/v1, עוגיות, והכותרת X-CDC-Request: 1 שהשרת דורש בבקשות ששומרות או משנות נתונים.
  • אין לוגים עם מידע אישי: לא מיילים, לא טלפונים, לא טוקנים ולא הערות מנטורים.
  • טקסטים בממשק כתובים בעברית ישר בקוד (אין ספריית תרגום).
  • כל רשימה צריכה מצב טעינה (skeleton) ומצב ריק (EmptyState). מחיקה דורשת אישור.
  • צבעים, רדיוסים ופונטים לוקחים מהטוקנים ב־src/constants/theme.css, לא ערכי hex אקראיים. הטוקנים עצמם מועתקים מה־Claude Design: שינוי עיצובי נעשה קודם שם, ורק אחר כך בקוד.

7תהליך העבודה: ממשימה ועד merge

משימה בספרינט← ענף KAN-<n>-<slug>← PR עם מפתח Jira← CI + ריוויו← merge
  1. לוקחים משימה. ב־Jira, בספרינט הפעיל, משייכים לעצמכם משימה ומעבירים ל־In Progress. קוראים את קריטריוני הקבלה ואת הסעיפים ב־REQUIREMENTS ו־DESIGN שהמשימה מפנה אליהם. אם המשימה כוללת מסך, פותחים אותו ב־קובץ העיצוב ב־Claude Design. זה מה שהמסך צריך להיות.
  2. פותחים ענף מ־main מעודכן. שם הענף: מפתח ה־Jira ותיאור קצר באנגלית עם מקפים. 
    git checkout main && git pull
git checkout -b KAN-23-login-form
  3. כותבים קוד וטסטים, ומריצים מקומית pnpm lint, pnpm test, pnpm build. עושים commit קטנים עם הודעות ברורות. 
    git add .
git commit -m "feat(auth): add login form with zod validation"
git push -u origin KAN-23-login-form
  4. פותחים Pull Request ל־main. התבנית נטענת לבד: מה ה־PR עושה, מפתח ה־Jira (KAN-23), וצ׳קליסט. מפתח ה־Jira בשם הענף ובתיאור מקשר את ה־PR למשימה ב־Jira אוטומטית. אם המשימה נוגעת בשני הריפוזיטוריז, פותחים PR בכל אחד.
  5. בדיקות אוטומטיות וריוויו.
    • GitHub Actions מריץ: install → lint → prettier → test → build. הכול חייב להיות ירוק.
    • Vercel מעלה גרסת Preview עם לינק משלה, כדי שאפשר לראות את השינוי באוויר.
    • CodeRabbit (בוט AI) משאיר הערות. קוראים, מתקנים או עונים למה לא.
    • אחד הלידים (לפי CODEOWNERS) עושה ריוויו ומאשר. כל commit חדש מבטל אישור קודם.
  6. Merge. אחרי אישור, CI ירוק וכל השיחות סגורות, אתם (כותבי ה־PR) עושים merge. המיזוג ל־main מעלה לפרודקשן אוטומטית. מעבירים את המשימה ב־Jira ל־Done.
מתי משימה נחשבת גמורה (Definition of Done) קריטריוני הקבלה מכוסים בטסטים או נבדקו ידנית ונכתבו ב־PR; ה־CI ירוק; היה ריוויו; המסכים עובדים עם מקלדת בלבד ונראים טוב ברוחב 360px.

11תקלות נפוצות

pnpm: command not found

התקינו אותו: npm install -g pnpm@10.32.1. אם החלפתם גרסת Node עם nvm, צריך להתקין שוב לגרסה החדשה.

שגיאת engines / Unsupported engine בזמן pnpm install

גרסת ה־Node ישנה מדי. הריצו nvm install 22 && nvm use 22 וודאו ש־node --version מראה לפחות v22.22.2.

השרת לא עולה: Invalid environment variables

הבדיקה של env.ts נכשלה. ההודעה מראה איזה משתנה. בדקו שהעתקתם את .env.example ל־.env ושהערך בפורמט הנכון (לדוגמה, MONGODB_URI חייב להיות כתובת מלאה).

EADDRINUSE: address already in use :::3000

משהו אחר כבר משתמש בפורט. סגרו את התהליך הישן, או שנו את PORT ב־.env ואז גם את DEVELOPMENT.API_TARGET באתר.

באתר, קריאות ל־/api נכשלות עם 500 או ECONNREFUSED

השרת לא רץ, או רץ על פורט אחר. הריצו את השרת (pnpm dev בריפו של השרת) ובדקו את curl http://localhost:3000/api/v1/health.

ה־commit נחסם על ידי Husky

זה lint-staged שמצא שגיאת lint. תקנו את מה שמופיע בטרמינל (הרבה פעמים pnpm lint --fix מספיק), הוסיפו שוב עם git add, ונסו שוב.

ה־CI נכשל על no-physical-direction

השתמשתם במחלקה כמו ml-2 או text-right. החליפו בגרסה הלוגית (טבלה בסעיף 6).

ה־CI נכשל על Prettier

הריצו pnpm format, עשו commit ו־push.

תקועים יותר מחצי שעה? כתבו בקבוצת הצוות מה ניסיתם ומה השגיאה המדויקת.
